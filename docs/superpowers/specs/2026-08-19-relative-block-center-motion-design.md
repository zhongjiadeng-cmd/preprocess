# 相对坐标与分块中心运动设计

## 目标

加工文件中的机床运动统一使用相对坐标模式。当用户启用 Voronoi 分块并勾选“按加工块中心移动 XY”时，每个非空加工块生成独立 patch；机床按实际加工顺序相对移动到各块中心，patch 内的 XY 坐标转换为以该块中心为原点的局部坐标。

本功能必须同时满足以下安全约束：

- 第一条机床指令进入 `G91`，加工过程中保持相对坐标模式，最后一条指令追加 `G90`。
- 加工结束后不额外返回加工区域原点，机床停在最后一个非空加工块中心。
- DXF 中用于 CAD 检查的四条加工区域边框不进入分块加工 patch。
- 缺失或不一致的分块元数据必须导致生成失败，不允许依靠 LINE 顺序猜测后继续输出。

## 用户界面

主流程的“机器加工文件”区域新增复选框：

```text
按加工块中心移动 XY
```

行为如下：

- 默认勾选。
- “加工块数量”大于 `0` 时可用。
- “加工块数量”为 `0` 时自动禁用，生成器按未分块模式运行。
- 用户取消勾选后，即使 DXF 含有分块，也继续使用每层一个 patch，不执行块间 XY 机床移动。

命令行生成器提供等价的布尔开关，macOS 应用显式传递开关状态，不依赖脚本默认值推断界面选择。

## 方案选择

采用“DXF 加同名分块元数据 JSON”的方案。生成 Hatch DXF 时已经拥有准确的 Voronoi 中心、块输出顺序和每块 LINE 数量，因此由该阶段写出元数据；加工文件生成器只消费和验证元数据，不重新计算 Voronoi，也不根据扫描线回跳推断块边界。

未采用的方案：

- 不把元数据嵌入 DXF 图层或注释，避免改变当前极简 DXF 格式以及第三方软件重存时丢失信息。
- 不从 LINE 顺序和包围盒反推分块，避免斜向 Hatch、空块、毛边和不规则块造成误判；包围盒中心也不等于实际 Voronoi 中心。

## 分块元数据

每个分层 DXF 旁生成同名的分块元数据文件。若 DXF 名为：

```text
layer_01_gray_lt_255.dxf
```

元数据名为：

```text
layer_01_gray_lt_255.blocks.json
```

元数据至少包含：

```json
{
  "version": 1,
  "border_line_count": 4,
  "blocks": [
    {
      "block_index": 3,
      "center_x": 12.345,
      "center_y": -6.789,
      "line_count": 428
    }
  ]
}
```

字段语义：

- `version`：元数据格式版本，首版固定为整数 `1`。
- `border_line_count`：DXF `ENTITIES` 开头、加工块之前的检查边框 LINE 数量；未写边框时为 `0`，写边框时为 `4`。
- `blocks`：严格按 DXF 中块的实际输出顺序排列，而不是原始 Voronoi 索引顺序。
- `block_index`：原始 Voronoi 块编号，仅用于诊断和日志。
- `center_x`、`center_y`：该块用于机床定位的 Voronoi 种子坐标，单位为毫米。在当前 Lloyd 松弛流程结束后，该坐标就是生成阶段持有的块中心。
- `line_count`：该块连续写入 DXF 的 LINE 数量，可以为 `0`。

元数据使用有限数值，禁止布尔值冒充整数或数字。`border_line_count + sum(block.line_count)` 必须等于 DXF 中 LINE 总数。块编号必须唯一，块列表不能为空，中心坐标必须为有限数值，所有计数必须为非负整数。

元数据是 DXF 阶段和加工打包阶段之间的中间产物，不复制到最终机器加工目录。最终目录仍只包含：

```text
machine.json
patches/<patch_index>_0.npy
```

## Patch 生成

### 启用块中心运动

加工文件生成器逐层读取 DXF 和对应元数据：

1. 验证元数据并核对 LINE 总数。
2. 丢弃开头 `border_line_count` 条检查边框。
3. 按每块 `line_count` 对剩余 LINE 进行无重叠、无遗漏的连续切分。
4. 跳过 `line_count == 0` 的空块；不为其生成 patch，也不让机床移动到该中心。
5. 对每个非空块，把每条线段的 `X1`、`X2` 减去 `center_x`，把 `Y1`、`Y2` 减去 `center_y`。
6. 按“层顺序，再按该层块输出顺序”分配全局连续 patch 编号。

每个 patch 继续使用 little-endian `float32`、`(N, 6)` 结构。Z 坐标保持现有 patch 约定：第 `i` 层两端 Z 均为：

```text
-i × 层间下降深度
```

因此，本功能只把 patch 的 XY 变为块中心局部坐标，不改变 patch Z 的现有含义。

局部坐标可以无损验证到浮点容差范围：

```text
local_xy + block_center == original_dxf_xy
```

### 未启用块中心运动

保持每层一个 patch：

- 不要求存在 `*.blocks.json`。
- 不排除检查边框，维持当前未分块打包行为。
- patch XY 保持 DXF 全局坐标。
- patch Z 仍为 `-i × 层间下降深度`。

## Machine cycle 与 G 代码

所有模式下的机床 G 代码都使用相对坐标运动，数值单位为毫米并保留三位小数，进给格式保持 `F40`。

### 通用模式切换

- 第一条指令以 `G91` 开始。
- 中间指令不重复写 `G91`。
- 最后一条指令以 `G90` 结束。
- 单个 patch 的加工任务同时满足“第一条”和“最后一条”，格式包含 `G91...G90`。

### 启用块中心运动

生成器维护上一加工位置：

- 初始机床 XY 位置视为加工区域原点 `(0, 0)`。
- 第一个 patch 的 XY 位移为其块中心减 `(0, 0)`。
- 后续 patch 的 XY 位移为“当前块中心减上一非空块中心”。
- 同层换块时 Z 位移为 `0.000`。
- 进入新一层的第一个非空块时 Z 位移为负的单层下降深度。
- 跨层时 XY 块中心差和 Z 单层下降量写在同一条 `G00` 指令中。

例如上一块中心为 `(10, 5)`，下一块中心为 `(18, 2)`，且仍在同一层：

```gcode
G00X8.000Y-3.000Z0.000F40
```

若该移动同时进入下一层且层间下降为 `6 μm`：

```gcode
G00X8.000Y-3.000Z-0.006F40
```

每个 `machine_cycle` 引用对应的全局 patch 编号：

```json
{
  "galvo_0": [
    0,
    "G00X8.000Y-3.000Z-0.006F40",
    [17, 0]
  ]
}
```

### 未启用块中心运动

- 每层对应一个 patch 和一个 `machine_cycle`。
- 所有 XY 位移为 `0.000`。
- 第一层 Z 位移为 `0.000`。
- 后续每层固定写一次负的单层下降深度，不再写累计绝对 Z。

三层、下降深度 `6 μm` 的完整序列为：

```gcode
G91G00X0.000Y0.000Z0.000F40
G00X0.000Y0.000Z-0.006F40
G00X0.000Y0.000Z-0.006F40G90
```

加工结束不生成返回原点的额外指令。

## 生成流程与接口

Hatch 生成器负责：

- 返回或构造按 DXF 输出顺序排列的块描述。
- 分别写入同目录临时文件并完成内容校验后，再发布 DXF 与对应 `*.blocks.json`；主流程只有在两者都存在且可验证时才把该层视为生成成功。
- 在日志中显示元数据路径、有效块数和空块数。

加工文件生成器负责：

- 接收是否启用块中心运动的明确参数。
- 启用时逐层读取、验证并消费元数据。
- 构造有来源层号、块中心和局部 LINE 的 patch 计划。
- 从同一 patch 计划生成 NPY 文件与 `machine_cycle`，避免编号、运动顺序和文件内容分别计算后产生偏差。
- 在最终发布目录之前重载并验证所有生成物。

macOS 应用负责：

- 根据加工块数量更新复选框可用状态。
- 将用户选择显式传给加工文件生成脚本。
- 保持当前每层使用不同、可复现的 Voronoi 种子行为，因此不同层可以拥有不同块中心；跨层 XY 相对运动必须使用各层实际元数据计算。

## 错误处理

启用块中心运动时，以下任一情况必须在发布最终目录前失败：

- 对应 `*.blocks.json` 不存在、不是普通文件或无法解析。
- `version` 不是 `1`。
- 根对象或块对象包含缺失、额外或类型错误的字段。
- 中心包含 NaN 或无穷值。
- 计数为负数、非整数或布尔值。
- 块编号重复。
- 元数据声明的 LINE 总数与实际 DXF 不一致。
- 所有块均为空，因而没有可加工 patch。
- 局部坐标转换或 float32 写入后产生非有限数值。
- 生成的 patch 文件集合、编号或 `machine_cycle` 引用不一致。

失败时沿用现有临时目录、所有权令牌和无覆盖发布机制，清理范围不得扩大。

## 验证与测试

Python 单元和集成测试覆盖：

- 元数据按实际块输出顺序记录中心和 LINE 数量。
- 包含与不包含检查边框时的 `border_line_count`。
- 块 LINE 连续切分、空块跳过和边框排除。
- patch 局部 XY 加中心后还原原 DXF 坐标。
- patch Z 保持层累计深度约定。
- 第一条 `G91`、最后一条 `G90`，中间不重复切换模式。
- 同层中心差、跨层中心差以及跨层相对 Z。
- 未分块或关闭设置时每层一个 patch，并使用相对 Z。
- 单层单块任务同时包含 `G91` 和 `G90`。
- 元数据缺失、版本错误、字段错误、非有限中心、计数不匹配、重复编号和全空块均被拒绝。
- CLI 开关能够控制两种模式，生成后验证器能够发现篡改。

macOS 应用验证覆盖：

- 默认勾选状态。
- 分块数量为 `0` 时禁用，恢复为正数时重新可用且保留用户选择。
- 传给 Python 的参数与界面状态一致。
- 应用能够编译，三步主流程的既有参数和取消清理逻辑不回归。

最终人工冒烟验证使用至少两层、每层至少两个非空块的数据，检查：

- patch 数量等于所有层非空块数量之和。
- 每层第一块以外的同层指令 Z 为 `0.000`。
- 每层第一块的 Z 除第一层外均为固定负层间深度。
- 累加全部 XY 相对位移后，每一步位置等于相应块中心。
- DXF 检查边框不出现在任何分块 patch 中。
- 最后一条指令追加 `G90`，且不存在返回原点运动。
