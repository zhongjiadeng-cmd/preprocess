# TIFF 兼容与纹理/DXF 共用预览区设计

## 背景与根因

现有功能在主流程和“纹理转 Hatch DXF”页面导入纹理后，使用 Pillow 读取像素与 DPI，再使用 Avalonia/Skia 直接解码图片用于预览。用户提供的 `30X30-40C-240u-FK.tif` 是有效的单页 8 位灰度 TIFF，尺寸为 1500 × 1500 px，内置分辨率为 1270 × 1270 DPI。Pillow 和 macOS 均可正常读取，但 Avalonia/Skia 的 `Bitmap.DecodeToHeight` 无法解码该 TIFF，并在内部空对象上触发异常。因此当前界面只显示笼统的“无法读取图片”。

同时，纹理预览目前位于左侧参数区的小卡片中，而 DXF 使用右侧大画布。该布局不符合“纹理与 DXF 在同一窗口位置预览，并在 DXF 生成后切换观察”的要求。

## 目标

- 可靠预览 Pillow 支持的 TIFF、PNG 等纹理图片，包括上述故障样本。
- 保留现有像素、DPI、物理尺寸换算和目标宽高可手动覆盖行为。
- 让纹理图片和 DXF 复用页面右侧同一个大预览区域。
- DXF 生成或导入后可在“纹理图片”和“DXF”之间随时切换。
- 在两个相关页面中保持一致行为，并重新生成 Release 构建。

## 范围

修改覆盖：

- 主流程“灰度分层 → Hatch DXF → 加工文件”。
- “纹理转 Hatch DXF”独立页面。
- Python 图片检查/预览输出、C# 图片读取模型、预览状态控制和相关测试。

不修改纹理转 DXF 算法、原始图片内容、DXF 绘制算法或机器加工文件格式。单独的“灰度图分层”页面不在范围内。

## 方案选择

### 预览布局

采用方案 A：在现有右侧大预览区标题栏增加“纹理图片”和“DXF”两个标签，共用同一画布位置。

- 导入纹理成功后自动选择“纹理图片”。
- DXF 生成成功或导入成功后自动选择“DXF”。
- 自动选择只改变当前可见内容，不释放另一种预览；用户随后可手动往返切换。
- 两个标签始终可见。尚无对应内容时，该标签页显示明确空状态。
- 移除左侧参数区原有的小型纹理图片预览卡片，避免重复占用空间。

不采用左侧缩略图栏方案。缩略图能持续提示两种内容，但会挤占大画布宽度，且只有两种预览时增加了不必要的界面复杂度。

### TIFF 解码

Pillow 已经是转换后端对图片格式与 DPI 的权威读取器，因此扩展现有只读图片检查模式，让它在同一次调用中返回：

- 像素宽高与可选 X/Y DPI。
- 按预览最大边约束等比例缩放后生成的 PNG 数据。

PNG 预览通过 Base64 包含在结构化 JSON 中，由 C# 在内存中解码后交给 Avalonia 显示。这样 Avalonia 只需要读取其稳定支持的 PNG，不再直接读取 TIFF。整个过程不创建临时图片、不覆盖源文件，DXF 转换仍使用原始输入路径。

不采用磁盘临时 PNG，因为它会引入命名、权限、取消和清理问题。不增加新的第三方 C# 图片库，以避免重复维护与 Pillow 不一致的格式/DPI 语义。

## 界面与状态

共同预览面板包含：

- 标题“实际预览”。
- 顶部“纹理图片 / DXF”标签切换。
- 中部复用画布位置。
- 纹理标签下方的信息栏：像素尺寸、DPI、计算后的物理尺寸或等待 DPI 状态。
- DXF 标签下保留现有层选择器、适应窗口、方向箭头、缩放和平移能力以及 DXF 状态信息。

状态规则：

1. 初始状态：两个标签均可进入，各自显示空状态。
2. 图片读取中：切到纹理标签，画布显示读取状态。
3. 图片读取成功：显示等比例预览及元数据，并按既有规则自动计算目标宽高。
4. 图片读取失败：纹理标签显示简短的具体失败原因，不修改目标宽高。
5. DXF 生成或导入成功：保留纹理预览，切到 DXF 标签显示结果。
6. 再次导入图片：替换旧纹理预览并切回纹理标签；现有 DXF 状态不被无关清除，除非当前流程本身开始新一轮生成并按既有规则清空结果。

目标宽高仍可手动编辑。成功导入带 DPI 的新图片，或缺少内置 DPI 时填写有效备用 DPI，才会触发自动写入；其他标签切换和预览操作不会覆盖手工值。

## 组件边界与数据流

Python 负责图片格式兼容、元数据读取和预览像素生成。预览输出必须限制尺寸并使用确定的 PNG 编码，避免把原始大图完整塞入 JSON。

C# 图片信息模型负责验证 JSON 字段、Base64 和预览数据，并创建可释放的 Avalonia 位图。纹理预览控制器继续负责导入串行化、取消、旧位图释放、尺寸计算触发与稳定状态，不承担 DXF 解析。

页面级共同预览容器只负责切换两个已经独立维护的内容视图。DXF 预览控件保持现有职责；纹理导入成功和 DXF 加载成功分别向容器发出选择对应标签的动作。

数据流如下：

1. 用户选择源图片。
2. Python/Pillow 在同一次只读检查中读取元数据、生成受限尺寸 PNG，并输出 JSON。
3. C# 验证 JSON，将 Base64 PNG 解码为内存位图。
4. 纹理控制器原子地替换旧预览、更新元数据与必要的目标尺寸。
5. 页面共同预览容器选择纹理标签。
6. 后续 DXF 生成或导入成功时，现有 DXF 控件加载文件，共同预览容器选择 DXF 标签。

## 错误处理与资源管理

- Pillow 无法识别、文件损坏、预览数据无效、Python 不可用或文件读取失败时，应用不退出，目标宽高不被覆盖。
- 界面显示可操作的具体原因，例如“Python/Pillow 不可用”“图片数据损坏”或“预览数据无效”，同时将完整异常写入诊断日志。
- Python 预览数据设定最大边限制，C# 同时验证解码后的尺寸，防止异常输出造成无界内存使用。
- 新导入请求取消旧请求；过期请求不得覆盖新图片、切换标签或写入尺寸。
- 替换图片、取消、失败和窗口关闭时均释放候选位图及旧位图。
- Base64 解码和位图创建全部在内存中完成，不产生需要清理的预览文件。

## 测试与验证

实现采用测试驱动方式，至少覆盖：

- Python 对上述 1500 × 1500、1270 DPI 灰度 TIFF 返回正确元数据与可解码 PNG 预览。
- PNG、无 DPI 图片、横纵 DPI 不同图片保持原有语义。
- 预览最大边约束、宽高比和 Base64/PNG 输出验证。
- C# 对有效预览、损坏 Base64、无效像素尺寸和过大预览的处理。
- 快速连续导入时只有最新请求能更新纹理视图、目标尺寸与当前标签。
- 导入图片自动选择纹理标签；DXF 生成或导入成功自动选择 DXF；手动标签切换不改变两侧内容状态。
- 图片失败不修改目标宽高，标签切换不覆盖手动尺寸。

完成后运行完整 Python 测试、完整 C# 测试和 `dotnet build -c Release`。界面验证使用用户提供的 TIFF，并在两个页面分别检查：

1. TIFF 能显示预览、1500 × 1500 px、1270 × 1270 DPI 和 30 × 30 mm。
2. 目标宽高自动填写为 30 × 30 mm 后仍可手动修改。
3. DXF 生成成功后自动切换到 DXF。
4. 点击“纹理图片”可回看原图，再点击“DXF”可回看生成结果。

## 验收标准

- 用户提供的 TIFF 不再显示“无法读取图片”。
- 图片与 DXF 在同一右侧画布位置预览，没有左侧重复小预览。
- 导入图片和 DXF 成功时按规则自动切换，且用户可随时手动切换。
- 像素、DPI、物理尺寸和自动尺寸计算准确；目标宽高仍可编辑。
- 失败状态具体、稳定，不导致崩溃或错误覆盖尺寸。
- 两个相关页面行为一致，自动化测试通过，Release 构建成功。
