# DXF 预览使用分块元数据设计

## 目标

删除 DXF 预览器根据 LINE 几何顺序猜测加工块和检查边框的重复逻辑。预览器改为读取 DXF 同目录、同名的 `*.blocks.json` 侧车文件，并使用生成阶段记录的准确边框数量、块顺序、块编号和每块 LINE 数量进行着色。

没有配套分块元数据的普通 DXF 仍可预览，所有 LINE 使用统一颜色。

## 当前问题

`DxfPreviewControl` 当前执行两次 DXF 扫描，并通过以下启发式规则分析加工块：

- 第一遍只要发现竖直 LINE，第二遍就把开头四条 LINE 当作检查边框。
- 非边框 LINE 的 Y 坐标回到更高位置时，推断进入了下一个加工块。

生成阶段已经写出版本化的 `*.blocks.json`，机器加工打包阶段也以该文件作为唯一准确来源。预览器再次推断相同信息会产生重复实现，并可能在斜向 Hatch、空块、非生成器 DXF 或不同实体顺序下错误分块。

## 方案选择

采用由 `DxfPreviewControl` 自动查找、解析和验证同名分块侧车文件的方案。预览控件拥有 DXF 实体扫描和着色逻辑，因此也应拥有预览所需的元数据映射，避免把文件格式细节扩散到 `MainWindow`。

未采用以下方案：

- 元数据损坏时静默退回单色预览。这样会掩盖生成阶段产生的 DXF 与元数据不一致，用户可能把错误预览当作正确分块。
- 由 `MainWindow` 解析 JSON 后传入预览控件。这样会增加界面编排层与预览文件格式之间的耦合。
- 保留原有几何启发式作为回退。没有 JSON 时统一单色已经满足普通 DXF 的预览需求，继续猜测只会保留本次要删除的冗余行为。

## 元数据契约

若 DXF 路径为：

```text
layer_01_gray_lt_255.dxf
```

预览器查找：

```text
layer_01_gray_lt_255.blocks.json
```

侧车使用现有 v1 契约：

```json
{
  "version": 1,
  "border_line_count": 4,
  "blocks": [
    {
      "block_index": 3,
      "center_x": 12.345,
      "center_y": -6.789,
      "line_count": 428
    }
  ]
}
```

预览器对影响实体映射的字段执行严格验证：

- 顶层字段和每个块字段必须与 v1 契约完全一致。
- `version` 必须为整数 `1`。
- `border_line_count` 和 `line_count` 必须为非负整数。
- `blocks` 必须为非空数组。
- `block_index` 必须为非负且唯一的整数。
- `center_x` 和 `center_y` 必须为有限数值，确保预览端接受与机器加工端相同的有效文档。
- `border_line_count + sum(block.line_count)` 必须等于 DXF LINE 总数。

存在侧车但文件为空、不是普通文件、JSON 无效、字段无效或计数不一致时，当前 DXF 预览失败，并通过现有状态栏错误路径显示原因。

## 数据流

`LoadFile` 首先判断同名侧车是否存在：

1. 不存在侧车时，以无分块模式扫描 DXF。所有 LINE 的块编号统一为 `0`，所有 LINE 都不是检查边框。
2. 存在侧车时，读取并验证文档结构，建立按 DXF 实体序号排列的范围：先是 `border_line_count` 条边框，随后是各块连续的 `line_count` 条 LINE。
3. 第一遍 DXF 扫描取得准确 LINE 总数和模型边界，并据此验证元数据总计数。
4. 第二遍扫描在抽样收集 LINE 时，使用原始实体序号查找对应范围。边框实体标记为边框；加工实体使用 JSON 中的原始 `block_index`。
5. 现有绘图器继续以块编号选择颜色，以边框标记选择边框画笔；行合并、方向箭头、缩放和视图逻辑保持不变。

实体归属只由原始 DXF LINE 序号决定。即使第二遍为了大文件响应速度只收集部分 LINE，抽样结果仍映射到正确加工块，不按抽样后的列表位置重新分块。

## 界面行为

- 有有效侧车时，状态摘要显示 DXF 文件名、LINE 数量和“加工块 N 个”。这里的 N 是 JSON 中记录的块数量，包括 `line_count == 0` 的空块。
- 没有侧车时，状态摘要只显示文件名和 LINE 数量，不显示“分析出”或其他推断性文案，预览线统一使用第一种块颜色。
- 超过显示上限时继续显示抽样 LINE 数量。
- 手动导入 DXF 的流程不变，无需用户另选 JSON；预览器只查找约定的同名侧车。
- 有侧车但无效时不降级，现有“无法预览”状态显示具体元数据错误。

## 代码边界

- `GrayscaleLayersMac/DxfBlockMetadata.cs`：提供内部不可变元数据模型、严格侧车读取与验证，以及实体序号到边框/块的纯映射方法。
- `GrayscaleLayersMac/DxfPreviewControl.cs`：消费内部元数据映射；删除竖线检测、Y 回跳检测和推断块数量。
- `GrayscaleLayersMac.Tests/`：通过测试程序集可见的内部 API 覆盖元数据读取与范围映射，并通过公开的 `Summary` 覆盖预览降级行为；不新增公共 API。
- `GrayscaleLayersMac/README.md`：说明 DXF 预览和机器加工打包都消费同名 `*.blocks.json`；没有侧车的普通 DXF 采用单色预览。

不修改 `texture_to_hatch_dxf.py` 的侧车格式，也不修改 `dxf_to_machine_file.py` 的读取或校验规则。

## 测试策略

测试以小型、确定性的 DXF 和 JSON 临时文件验证真实文件读取行为：

- 有效侧车按 `border_line_count` 和各块 `line_count` 映射实体，并在摘要中报告 JSON 块数。
- 没有侧车时加载成功、摘要不报告加工块，所有实体采用同一块编号且没有边框标记。
- 存在但格式损坏的 JSON 导致加载失败。
- 顶层或块字段缺失、额外字段、错误类型、重复或负块编号、非有限中心、负计数均被拒绝。
- 元数据计数总和与 DXF LINE 总数不一致时被拒绝。
- `line_count == 0` 的空块保留在摘要数量中，但不消费 LINE。
- 抽样收集跨越块边界时，收集到的实体仍使用其原始实体序号对应的块编号。
- 现有纹理叠加、方向箭头、共享预览选择和 Python 测试保持通过。

## 成功标准

- `DxfPreviewControl` 中不再存在通过竖直 LINE、固定四条边框或 Y 坐标回跳分析加工块的逻辑。
- 分块颜色与现有 `*.blocks.json` 的实际块顺序和编号一致。
- 没有侧车的 DXF 可继续单色预览。
- 存在但无效或不匹配的侧车不会被静默忽略。
- 状态栏不再使用“分析出加工块”的措辞。
- C# 与 Python 自动化测试全部通过。
