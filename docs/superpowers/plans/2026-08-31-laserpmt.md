# LaserPMT Parameter Matrix Implementation Plan

**Goal:** Add a fourth LaserPMT pipeline step that expands explicit machining-parameter values into a physical workpiece matrix, emits independently runnable numbered JSON files plus a separately calculated `allmachine.json`, and adds a PMT wireframe preview without changing existing Texture or DXF behavior.

**Architecture:** A new standalone Python module owns matrix expansion, layout, package generation, vendor-motion recomputation, strict reload validation, and atomic publication. Focused C# domain types own UI-boundary parsing/readiness and layout presentation. A new PMT canvas consumes a typed layout manifest. `MainWindow` only binds controls, invokes the Python process, imports results, and coordinates the fourth step.

**Tech stack:** Python 3.9+, NumPy, standard-library `argparse/csv/json/pathlib`; C# 13 / .NET 10; Avalonia 11.3.x; NUnit and pytest.

## Global constraints

- Work only in `/Users/ccc/Desktop/preprocess/.worktrees/laserpmt` on `codex/laserpmt`.
- Preserve current Texture and DXF rendering and interaction behavior.
- Preserve source patch, layer, Hatch-line, and block order inside every matrix job.
- Generate numbered JSON motion independently from local origin; never derive it by slicing `allmachine.json`.
- Generate `allmachine.json` from global targets starting at workpiece upper-left, in increasing number order, with no serpentine reordering.
- Use one non-shared numeric patch-index range per job; do not deduplicate patch data.
- Support all editable first laser-group fields plus layer feed; the last visible matrix parameter changes fastest.
- Reject more than 1,000 combinations.
- Keep controller patch names `<global-index>_0.npy` and references `[global-index, 0]`.
- Preserve the existing path-identity, owner-lock, no-overwrite, and atomic-publication safety model.
- Add no new runtime dependency.
