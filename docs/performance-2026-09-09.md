# 第一轮性能优化验证

日期：2026-09-09。修改基于当前 src 目录中的工作区版本，保留已有目录迁移及其他改动。

## 改动

- Python DXF 读取按实体解析，坐标直接追加到紧凑 double 缓冲区，再由 NumPy 共享缓冲区，避免完整文本行、实体字典集合和坐标对象列表同时驻留。保留坐标完整性、有限数值和截断输入检查。
- DXF 预览按控件缓存固定调色板和方向箭头画笔，移除每帧为寻找加工块而进行的完整线段集合扫描。边框画笔仍读取当前主题，原有抽样和裁剪规则保留。
- PMT 在一次生成任务内按已加载来源对象、XY 缩放和层间进给缓存几何组。仅激光参数不同的任务复用数组及组编号；不同来源或几何参数仍生成并通过原有精确比较去重。时间戳继续使用原路径。最终输出验证保留。

## 对比结果

使用本轮修改前保存的 Python 文件与修改后的实现对比。

| 项目 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 60,000 条合成 LINE 的解析峰值分配（tracemalloc） | 71.98 MiB | 2.81 MiB |
| 同一 DXF 不开启 tracemalloc 的三次计时中位数 | 3.282 秒 | 1.695 秒 |

解析数组完全一致。内存数字是 tracemalloc 捕获的分配峰值，不是应用整体 RSS。计时受当前电脑负载影响，不代表整条加工流水线的加速比例。

PMT 对比使用两层基础 patch，每层将小型测试数据重复 10,000 次；生成 80 个仅功率不同的任务。两次对比的总耗时分别为 1.017→0.971 秒、1.605→1.025 秒，波动较大，因此不据此承诺固定加速比例。每次生成的全部 85 个输出文件均逐字节一致。

尚未测量真实桌面交互帧率；预览优化已通过相关桌面测试，但不声明帧率增幅。

## 第二轮：真实纹理的周期与切割边界计算

对 `30X30-40C-240u-FK.tif`（1500×1500）进行 cProfile 测量后，发现切割边界计算存在按相位反复复制大数组的成本。本轮改动：

- 按轴以 256 个位置为一块统计相邻黑色像素边界，再按相位汇总一维计数。保持原有匹配得分及并列时选择最小相位的规则。
- 周期候选仍按从小到大检查，发现第一个完全匹配便返回；没有完全匹配时，继续原有近似匹配峰值规则。
- 未更改阈值、裁剪尺寸、填充顺序、随机种子或 Voronoi 几何。

重复单元识别三次计时中位数（不包含读图）：

| 真实输入 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 30X30-40C-240u-FK.tif，1500×1500 | 0.2596 秒 | 0.2387 秒 |
| 网格纹理图.tif，5000×5000 | 7.0454 秒 | 6.2294 秒 |

小图单独的双轴切割边界计算五次计时中位数为 0.0619→0.0286 秒，选中的相位和分数完全相同。完整转换单次计时有明显波动，不应将这些局部收益当成整体加工速度的提升比例；以上是当前电脑环境中的参考值。

验证：Hatch 与新增原规则对比测试共 94 项通过；独立流水线及大 TIFF 限制测试共 10 项通过。新增对比覆盖随机噪声、完整周期、近似匹配、全黑全白、并列边界、跨 256 位置分块及两个轴。

两张真实纹理分别以 10×10 mm、0.02 mm 间距、0°/37°、9 个 Voronoi 块、随机种子 12345 转换。四组结果的 DXF 和 `.blocks.json` 均逐字节一致，提取的重复单元像素及位置、周期、分数完全一致。测试只读用户原始纹理，输出保存在临时目录。

## 第三轮：压缩行列的等价分组

`_axis_tokens` 原来使用 `np.unique(packed, axis=0)`，对压缩行中的多个字节字段排序。现在将连续的压缩行视为一个固定长度 `np.void` 记录后去重。没有使用概率哈希，全部字节（包括尾部零字节）都参与比较。标记编号只供相等性比较，不作为加工顺序；行列等价分组保持一致。显式处理空轴，返回一维标记数组。

以下对比基线是第二轮完成后的版本，而非项目最初版本。重复单元识别为三次计时中位数，不包含读图：

| 真实输入 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 30X30-40C-240u-FK.tif，1500×1500 | 0.1735 秒 | 0.0918 秒 |
| 网格纹理图.tif，5000×5000 | 5.5511 秒 | 0.4170 秒 |
| surf._U1_V1_e.tif，5326×5326 | 1.9148 秒 | 0.3862 秒 |

网格纹理在相同 10×10 mm、0.02 mm 间距、9 块条件下，完整函数转换单次计时：0° 为 6.2854→1.0726 秒，37° 为 6.1484→1.3754 秒。这些转换计时包含读取和输出，但不包含 Python 进程启动；单次值仅供参考，不等于所有图片或整个多层流水线的固定加速比例。

回归测试共 116 项通过。额外覆盖空轴、字节补齐、负步长、转置、全黑全白及重复图案的等价分组；周期参考实现保留旧版分组算法，避免测试和实现同时改用新算法而掩盖差异。

上述三张真实纹理分别在 0°、37° 下转换，共六组。每组 DXF、分块 JSON、配准预览 PNG 均与修改前逐字节一致；重复单元内容、位置和匹配得分也保持一致。所有输出位于临时目录，未覆盖原图或已有加工文件。

## 收尾：批处理、缓存检查与可重复测量

- 节点工作流的多层 Hatch 改为一次 Python 进程内依次处理，减少每层重复导入 NumPy/Pillow。沿用每层 CLI 参数、随机种子和顺序，提前解析所有任务参数，失败即停止后续任务；单层仍可直接调用。旧界面的逐层进度路径保留。
- 缓存配置已改变、上游已重算或旧任务失败时，不再完整读取旧产物计算无用哈希。能够复用的结果、执行前后输入和新输出仍进行内容校验。
- 增加 `tools/profile_preprocessing.py`，支持真实图片的灰度分层、Hatch、Machine、PMT 分阶段耗时与进程历史峰值 RSS 记录，以及可选 cProfile 文件。输出目录必须为新目录，失败时也保存测量结果。

运行示例（输出目录必须不存在）：

```bash
python3 tools/profile_preprocessing.py input.tiff /tmp/preprocess-profile-new --layers 3 --size 10
```

`performance.json` 中的 RSS 是截至各阶段的进程历史峰值，不是各阶段独立峰值；计时不包括解释器启动、C# 端文件哈希和 UI 渲染。已使用真实 1500×1500 纹理成功完成三层四阶段试跑。
